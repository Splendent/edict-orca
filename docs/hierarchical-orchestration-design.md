# Edict 三省六部團隊協作設計

設計日期：2026-11-05。架構決策：採各省部頭領管理執行代理的組織；本文件定義待實作的行為與驗收條件。階層式派工的執行支援屬條件可行，須通過第 11 節的實測才能宣告可用。

執行適配以本機 Orca 1.4.249 的靜態程式核對為依據。已確認同 Run 下屬、直接頭領回報及原生請求收據的程式路徑；跨程序交錯與各代理種類仍未實測。控制承諾限於關閉新准入及可追查地收斂在途工作，不承諾控制回覆後不存在任何稍後的實體啟動。研究證據、反例與可執行模型見[控制語義研究](research/control-semantics.md)。

## 1. 目標與範圍

一次需求可包含多個工作項目。中書、門下及六部均可在自己內部分派工作，由頭領負責共同決策、品質與對外交涉。尚書負責六部之間的調度與整合。使用者只與原對話交代工作，不必替部門選擇執行代理或逐次轉交成果。

### 1.1 必須成立的行為

1. 多件獨立工作的調查、規劃、審查與實作，可以分別交給不同代理執行；頭領不必親自完成全部細節。
2. 每個工作項目各自規劃、放行、派工及驗收。共同介面、資料與安全前提仍按真正相依等待。
3. 頭領負責本團隊分工與審核；跨省部的正式要求與交付由頭領交換，沿用三省六部的職權。
4. 所有團隊共用派工、檔案與工具資源管理。增加頭領不得繞過總量限制或擴大使用者授權。
5. 子代理完成、團隊驗收、方案放行、整合驗收及門下結案確認分別判斷；使用者可暫停、取消與恢復指定工作，所有交接及決定均可追查。

### 1.2 邊界

本設計涵蓋組織、權限、資料、派工、訊息、審核、恢復、設定與驗收。首次實作以同一 Orca 主機、同一工作專案為範圍；跨主機團隊與跨專案共同交易不列入首版支援承諾。

手動 init、對話識別、Cursor 模式確認及 off 的啟用範圍繼續有效。沒有 init 的對話不自行啟用。不建立背景輪詢、聊天 hook 或自訂常駐模型程序。

本方案只設計新版資料與新建立的階層工作；舊 CLI、舊資料、舊 Run、格式遷移、相容轉接、跨版本續辦、並存版本路由與降版均不在範圍。此決定不授權清除或改寫現有資料；實作與驗收使用獨立的新版狀態目錄。

GitHub repo 設定、聊天選單外觀及自動發布不在本設計的修改範圍。流程中的 commit、merge、push、部署與對外傳送仍依使用者授權和專案規則執行。

## 2. 組織與職位

### 2.1 頭領與執行代理

省部使用既有角色 ID；職位是成員身分，不另建立一套部門 ID。每個 Run 的每個省部最多有一個有效頭領身分。頭領可負責多個工作項目，不為每件事重建一位頭領。

| 省部 | 角色 ID | 頭領職位 | 所屬執行職位與責任 |
| --- | --- | --- | --- |
| 中書省 | zhongshu | 中書令 | 中書舍人，負責分項調查、方案與驗收設計 |
| 門下省 | menxia | 侍中 | 給事中，負責分項方案的獨立審查 |
| 尚書省 | shangshu | 尚書僕射 | 管理六部尚書；大量調度證據可委派左右司郎中核對 |

原對話履行太子的需求整理與回報責任，負責啟動三省頭領、保留使用者授權及處理需要使用者決定的事項。它不逐件重做省部頭領的判斷。尚書的內部佐理代理沒有管理六部的獨立授權，只能提出核對結果。

| 六部 | 角色 ID | 頭領職位 | 所屬郎中的軟體工作 |
| --- | --- | --- | --- |
| 吏部 | libu_hr | 吏部尚書 | 代理設定、技能與權限配置 |
| 戶部 | hubu | 戶部尚書 | 資料處理、統計、資源及成本分析 |
| 禮部 | libu | 禮部尚書 | 文件、規範、介面文案與對外草稿 |
| 兵部 | bingbu | 兵部尚書 | 工程實作、測試與獨立程式審查 |
| 刑部 | xingbu | 刑部尚書 | 品質保障、程式審查、測試驗收、安全與合規稽核 |
| 工部 | gongbu | 工部尚書 | 建置、CI、部署與工具 |

同一部可有多位郎中，以成員 ID 與任務區分，例如「兵部郎中／初始化實作」「兵部郎中／更新器審查」。作者與審查者不得是同一個成員，也不得由同一份製作上下文冒充獨立審查。

官名採唐制名稱作軟體分工用途；郎中在歷史上是各司主管，本設計將其簡化為個別工作負責者。侍郎、員外郎、主事等不自動建立為額外管理層。太子作為需求整理者屬軟體改編。欽天監、早朝官等既有附加角色保留設定，本版不賦予三省六部的管理或跨部門派工權。

### 2.2 組織關係

```text
使用者
└─ 原對話／太子
   ├─ 中書令
   │  ├─ 中書舍人 A
   │  └─ 中書舍人 B
   ├─ 侍中
   │  ├─ 給事中 A
   │  └─ 給事中 B
   └─ 尚書僕射
      ├─ 吏部尚書 → 吏部郎中
      ├─ 戶部尚書 → 戶部郎中
      ├─ 禮部尚書 → 禮部郎中
      ├─ 兵部尚書 → 兵部郎中
      ├─ 刑部尚書 → 刑部郎中
      └─ 工部尚書 → 工部郎中
```

此圖表示管理與回報關係。三省間的方案、審查及派工交接另依第 3 節，不因組織圖的共同上層而全部經太子重新判斷。

六部尚書是尚書僕射的管理對象，也是各部郎中的頭領；因此本架構明確包含「尚書僕射 → 部尚書 → 郎中」。郎中、中書舍人與給事中不得再向下建立代理。多層關係由允許的職位組合檢查，不只用固定數字判斷深度。

### 2.3 建立與存續

頭領與下屬按實際需求建立。不使用的部門不啟動，不因有六部就先開六個團隊。能直接處理的小任務可由頭領完成，但仍須符合獨立審查要求。

頭領核對需求覆蓋、共同介面、關鍵風險、獨立審查及證據缺口，不重新調查每份原始資料或重跑每一項已具可信證據的測試。發現衝突或證據不足才深入對應部分。否則執行工作即使平行，仍會集中等待頭領重做全部工作。

頭領的邏輯成員 ID 在本 Run 內穩定；原生 Task、Dispatch 可因有界工作完成及續辦而改變，必須保存接續關係。實體代理關閉不等於邏輯頭領消失。續辦沿用原上下文；原上下文無法恢復時，以原始需求、決策、未解問題與成果交接，記錄替任及原因，不默默重開第二個有效頭領。

active 頭領可在自己所屬 Run 以原生 helper 路徑建立下屬。worker 不具有同 Run 協調者的完整 task-create 權限；不能把主對話的「先建全部原生 Task，再逐一派工」流程直接複製給頭領。同儕頭領仍 active 時可傳送交接訊息；已 settled 的同儕需要合法 owner 代喚醒，保留原發起者及核可，不由 owner 重新決定方案。直接頭領已結束而回落 root mailbox 的事件，依穩定成員映射轉交。

## 3. 職權與通訊

### 3.1 職權矩陣

| 呼叫者 | 可以建立或續辦 | 正式跨省部通訊對象 | 不允許的動作 |
| --- | --- | --- | --- |
| 原對話／太子 | 三省頭領 | 中書；接收整體回報及必要升級 | 繞過門下替方案批准、繞過尚書直接指揮六部 |
| 中書令 | 本省中書舍人 | 太子、侍中、尚書僕射 | 直接派六部實作、自行批准方案 |
| 侍中 | 本省給事中 | 中書令、尚書僕射 | 參與方案製作後仍宣稱獨立審查、派實作工作 |
| 尚書僕射 | 六部尚書及本省佐理代理 | 中書令、侍中、六部尚書 | 擴大核可方案、替門下放行 |
| 六部尚書 | 自部郎中 | 尚書僕射 | 指揮其他部門、自行擴大共同介面 |

所有執行代理只向自己的頭領報告成果或提問，沒有派工或正式跨部門通訊權。原對話對三省的啟動、原樣傳送使用者修正及只讀監督，屬控制操作；它不藉此跳過業務通訊矩陣。使用者明確改變授權時，先記錄新要求，再按受影響範圍重新分派。

控制操作與業務發起者分開記錄。原對話可建立空的頭領身分，但門下的審查任務必須有中書的方案送審要求，尚書的實作調度必須有中書轉交或門下核可交接；不能因原對話負責底層啟動就任意建立審查或實作要求。所有正式交接保留原發起者、版本及核可記錄。

跨部門交涉由尚書接收並轉交。例如禮部需要兵部確認選單行為，由禮部尚書向尚書提出具體問題，尚書將問題送兵部尚書；尚書不必請中書重新規劃。若需要改變共同介面，才回中書，受影響方案再送門下。

### 3.2 授權範圍與內部拆工

每個委派包含：來源工作、方案版本、可讀來源、可改範圍、工具資源、交付物、驗收、回報頭領與允許行為。子工作範圍必須是上層授權的子集，不得將「自行決定細節」解釋成增加功能或權限。

中書舍人的唯讀規劃、給事中的獨立審查，依頭領的階段授權執行，不要求它們先取得針對實作方案的門下核可，避免規劃必須先通過自身產出的審查。唯讀階段可寫任務指定的獨立暫存成果，不可改專案原始檔或外部系統。

六部的實作委派必須引用門下核可。部尚書可在核可範圍內拆工，不為每位郎中重新送門下；共同介面、範圍、安全前提或驗收發生變更，須停止尚未開始的相關派工並重審。已執行工作保留成果，由頭領通知變更，不根據方案失效自行中止程序。

提交成果與內部驗收的權限不包含門下的正式放行權。方案作者無論職位為何，均不能擔任該份方案的獨立審查者。

### 3.3 工具檢查與信任邊界

派工與傳送須根據 Orca 提供、並經確認的目前執行身分映射到成員，再查其職位及委派。不能只相信呼叫參數中的 `role`、`headId`、`--from` 或任務文字自稱身分。原對話 session ID 是對話識別，不是授權憑證；下屬不能因知道它就取得太子權限。

若 Orca 無法提供可驗證的呼叫身分，直接階層式權限檢查列為不支援。可設計由原生 owner 代送、保留真實來源及核可證據的執行介面，但須另通過同等身分與路由驗收，不能以主對話重新判斷每一項代替本架構。

上述限制防止正常代理經 Edict 入口意外越權，不構成同一作業系統帳號間的檔案、憑證或任意 shell 安全隔離。不能聲稱它能阻止代理繞過 Edict 直接操作其他工具；既有 sandbox 與原生權限仍須生效。

## 4. 多項需求的工作流程

### 4.1 需求拆分

一次指令在同一專案內建立一個 root Run，需求下分配穩定的工作項目 ID，例如 `W-001`、`W-002`。新增獨立目標建立新 Run；修正既有工作沿用原 ID。每個項目有獨立 workGeneration，與頭領替任的 generation 分開。需求項目與階段原生 Task 分開：同一項目可有規劃、審查、實作、整合與驗收 Task。

中書令先確認各項目是否獨立，再委派規劃舍人。共同介面由一個指定負責者擬定，其他規劃依其版本進行；不能讓不同舍人各自假定互不相容的介面。未知資訊列成具體調查工作，依範圍分派，不以無限調查取代可驗收的交付。

尚未確定的需求不得填入臆測答案。可以查證的問題先由團隊查證；會改變使用者意圖的決策經頭領升級原對話，一次詢問必要問題。

### 4.2 三省與六部的階段

1. 中書令分派規劃，核對舍人產出及交叉相依，將可獨立審查的方案單位送侍中。無需等同批無關方案齊備。
2. 侍中分派給事中，對明確版本逐單位記錄通過或退回。可行性、完整性、安全前提與驗收均有依據後才可放行。
3. 尚書接收核可單位，安排相關部尚書。各部尚書在授權內分派郎中；相依已齊且資源不衝突的工作可並行。
4. 部尚書核對成果、安排獨立審查或必要稽核，將通過的交付送尚書。內部缺陷交原作者修正；部門外的問題經尚書處理。
5. 尚書指定實作部門負責必要整合，安排獨立驗收，並將完整證據送門下確認結案。門下明確同意後才可標為 Done，再由尚書交中書令核對需求覆蓋、太子回報使用者。中書不重寫全部成果或取代驗收。

流程的正式回報沿原職權：六部 → 尚書 → 中書 → 太子；尚書在正式完成前，須經門下的結案確認。原對話可接收唯讀進度事件以回報狀態，不介入日常派工。共同未決事項只阻擋真正相依的項目。

### 4.3 完整範例

需求包含「聊天初始化設定流程」「Windows 更新器修正」「貢獻指引」，分別建立三個項目。

中書令派三位舍人；另由其中一位負責確認 共用設定介面。侍中可以在初始化與文件方案到達後先派兩位給事中審查，更新器方案仍由原舍人調查。核可資料及版本明確後，尚書分派兵部、禮部及必要的工部工作。

兵部尚書派初始化郎中與更新器郎中；兩者若改同一檔案，依檔案範圍依序執行或建立隔離子工作樹。兵部可安排內部審查，尚書另將方案要求的獨立程式審查、功能及安全驗收交刑部，刑部尚書派未參與製作的郎中執行。禮部可先寫與初始化介面無關的貢獻說明，初始化章節等待核定介面。工部處理 Windows CI 的必要變更。

初始化測試失敗，兵部尚書交原郎中修正，不將整件需求送回中書。若修正需要改核可的共用設定介面，兵部尚書回報尚書，尚書交中書處理變更，再由門下重審相關項目。其他獨立工作繼續。

各項實作與必要整合驗收完成後，尚書提交需求覆蓋、核可版本、刑部等獨立驗收及未解問題清單給門下。門下確認證據足以結案才記錄同意；不把收到最後一位郎中的成功回報視為需求已完成。

### 4.4 方案、成果與整體驗收

| 判斷 | 負責者 | 必要證據 | 不能拿來代替的訊號 |
| --- | --- | --- | --- |
| 分項方案可送審 | 中書令 | 需求、方案與相依完整 | 舍人聲稱規劃完成 |
| 實作方案放行 | 侍中 | 獨立審查、版本與逐項結論 | 給事中的原生 Task 成功完成 |
| 部門成果可交付 | 部尚書 | 實際差異、測試及必要獨立審查 | 郎中的 worker_done 成功 |
| 整體工作完成 | 尚書提出結案、門下確認、原對話回報 | 所有必要項目、獨立驗收、整合驗收與有效結案確認 | 原生 Task 全部 completed、尚書單方面宣告完成 |

刑部保留品質保障、程式審查、測試驗收、安全與合規責任，由尚書按方案安排；不能將它縮成只處理安全問題。兵部內部審核不取代方案要求的刑部獨立驗收。低風險文件不固定增加安全檢查；具體驗收種類與深度在方案中明訂，不由作者單方面免除。刑部若參與修正實作，須由未參與該份製作的其他成員驗收。

### 4.5 門下結案確認

方案放行與結案確認是兩個決定。方案放行允許實作；結案確認核對成果是否符合核可需求、必要獨立驗收及整合是否通過、是否仍有阻礙、暫停或未確認的副作用。門下不因此重新製作方案或重跑已有可信證據的全部測試。

尚書提交結案申請，引用確切方案、成果與驗收記錄。侍中可委派未參與製作的給事中核對，最終由有權門下成員明確記錄同意或退回。作者、執行部門、尚書及原對話均不能代替門下確認。Review 在確認前維持未完成；不新增使用者必須手動批准每件成果的步驟。

退回必須列出具體缺口；尚書交相應部門修正，涉及方案變更才回中書重新送審。修正後按新成果版本再次申請結案。方案或成果變更、必要驗收失效時，原結案確認同時失效。多項需求可以逐項確認，整體需求須等全部必要項目及共同整合具備有效確認後才為 Done。

| 資料 | 來源與保存位置 | Edict 責任 |
| --- | --- | --- |
| Run、Task、Dispatch 與執行狀態 | Orca | 保存索引及收據，查原生來源，不另建立執行狀態資料庫 |
| 對話啟用、設定與 Run 協作模式 | Edict session | 沿用原生對話 ID；更新不改其他對話 |
| 團隊、成員、工作項目與委派範圍 | Edict Run 協作記錄 | 保存身分關係、來源與版本，不以索引存在判斷正在執行 |
| 方案核可、內部驗收、整合驗收與結案確認 | Edict 不可變決策記錄 | 保存真實作者、審查者、成果版本與證據；查詢時計算有效性 |
| 方案、差異、報告與測試產物 | 可讀成果路徑及內容摘要值 | 確認來源、版本與修改範圍，不把大量輸出塞進所有代理上下文 |

Orca 的 `parent` 表示原生任務關係，不直接代表頭領擁有派工權；`deps` 表示啟動相依，不代表審查核可。團隊管理者、業務相依、工作樹父子關係三者分開記錄。

尚未滿足前置的工作是 Edict 委派意圖，不宣稱已有原生 pending Task。直接 helper 路徑在工作就緒後，使用 worker-start --spec 一次取得原生 Task 與 Dispatch；可帶實際已存在的 deps，parent 預設為建立 helper 的頭領 Task。若必須先建立完整原生 DAG，改由 Run owner 代建及代啟，並驗證回報轉交；不可讓 worker 冒充 owner。每個實作委派只屬於一個工作項目世代，共用頭領可同時管理多項委派。

以下是目標資料契約示例，識別碼均為佔位值，非現行 CLI 的可執行輸入。

  "session": "codex:example",
  "runId": "run-example",
  "mode": "hierarchical",


  "revision": 1,

每 Run 保存建立時的 Edict／Orca 版本、指引摘要與模型快照，僅供同版工作追查，不據此選擇並存程式或處理舊版資料。控制記錄包含 session active、Run pause、項目 pause，以及按工作世代保存的取消意圖；各層控制不能互相清除。

### 5.3 核可與成果版本

正式核可至少保存 `approvalId`、Run、工作項目、scope、方案版本與摘要值、門下頭領及實際審查者、審查 Dispatch、通過或退回結論、證據與時間。結論由有權成員的明確動作記錄，不讓協調者自行填一個 `approved` 就代表審查者認可。

任務核可限制輸入、允許修改範圍、共同介面與驗收，不綁定尚未產生的實作內容。成果驗收則綁定具體差異、基準 commit 或可重現的檔案快照與測試證據。

方案修正建立新版本及受影響項目集合；舊決策保留供追查。受影響的既有核可失效，無關項目保留有效性。修改成果後，舊成果驗收不能直接沿用；未改動範圍的證據經審查者確認仍可引用。

結案確認使用獨立的 `closure-confirmation` 決策種類，保存申請的工作項目或整合範圍、門下身分、方案與成果摘要值、必要驗收 ID、同意或退回及時間。它不能由 `plan-approval` 或 `artifact-acceptance` 自動生成。標記 Done 時，工具必須重新核對該記錄的職權、版本、需求覆蓋、完整證據及控制狀態。

所有核可、驗收與結案均綁定 workGeneration。接受晚到事實不等於接受其業務效果：先保存原生來源及去重，再核對控制順序、工作與成員世代、方案及成果版本，最後才可接受領域決定。仍有可能修改成果的委派或未知副作用時，不得提交 Done。Done 先合法提交後收到取消，回報該代已完成，不改寫歷史；取消先提交，晚到成功或結案決定只能歸檔。取消必要項目不會自動縮小原需求；需求減項須有明確變更及相應門下確認。

### 5.4 任務狀態與完成條件

使用者可見的工作項目狀態固定為 Backlog、Todo、WIP、Blocked、Review、Done。工作類別另使用 requirement、design、frontend、backend、testing、bug、docs、release、maintenance、misc，不與狀態混用。

該狀態是由原生執行資料與領域決策計算的呈現，不再建立可單獨覆寫的第二份執行狀態。原生 Task completed 只代表它已結束；方案退回、成果未驗收、必要整合未完成或缺少有效門下結案確認時，項目不能顯示 Done。Blocked 顯示具體阻礙與負責頭領。

尚未排入近期工作的需求呈現 Backlog；已排入但未開始為 Todo；已有執行、規劃或修正工作為 WIP；可交付成果已到齊且等待必要審查或結案確認為 Review；沒有可前進工作且有未解前置或失敗為 Blocked；所有必要驗收、整合與門下結案確認有效才為 Done。等待審查名額維持 Review，不能將等待視為審查通過。整個需求仍有獨立項目推進時呈現 WIP，並逐項列出 Blocked，不把整批都標成阻塞。人工暫停依第 8.4 節顯示控制狀態，不混入執行成功或驗收結果。

## 6. 派工與資源管理

### 6.1 單一准入檢查

所有建立、派工、續辦與重新喚醒，都必須經同一份協作規則。單項入口不得繞過批次入口的範圍、核可與資源檢查。頭領的直接派工採 helper --spec；尚未就緒時只保存委派意圖。task-create 及 owner 預建 Task 的啟動保留原生 owner 權限，不能因 Edict 提供同名命令就假設下屬可以直接使用。

`dispatch --spec-file`、`dispatch --task` 與重新開啟已結束代理的 continue 均須檢查，不能只在 dispatch-ready 驗證門下核可。讀取、原樣回報或結果保存不需取得新的實作核可；同一入口若會造成新實作、改變實作範圍或建立後續委派，就必須符合相應授權。任何入口都不能因省略必要參數而跳過檢查。

這些要求是待實作的修正：現行 beta.2 單項 dispatch 及 continue 沒有與批次入口相同的門下核可檢查，批次入口也仍由協調者填寫核可聲明。驗收必須證明各入口均在原生副作用前拒絕未核可實作，不能只修改提示文字就宣稱已完成。

每次啟動依序核對：身分與職位、工作世代與全部控制、委派及版本、原生前置完成、檔案與工具衝突、主機及本 Run 的剩餘額度。未滿足者保留原委派意圖，已有原生待辦者沿用其 Task；回傳具體原因與下一個需要的事件，不要求使用者手動重送任務。

派工分成可撤銷的預留與持久送出提交。短鎖內保留名額及範圍；送出提交時在同一把鎖內重新核對控制、世代及版本，保存不可變請求、原生請求 ID、真實呼叫身分與提交序號。pause、off、cancel 也取得這把鎖並提升控制 revision。控制先提交時撤銷尚未送出提交的預留；送出先提交時把該操作列為在途。禁止持鎖等待原生回應、代理啟動或模型工作。

此處的「在途」從持久送出提交開始，早於原生接受或實體代理啟動；這是對使用者明示的控制界線，不把本機記錄冒充 Orca 交易。鎖外請求仍可能在控制回覆後才抵達 Orca。原適配器能證明尚未執行任何原生 I/O 時，可將已提交操作記為未送出撤回；無法證明時保留在途，不能當作沒發生。嚴格禁止控制回覆後任何實體啟動，需要原生接收端的 epoch 檢查或可撤回請求，目前不列入已支援承諾。

Orca 已有 caller fingerprint 加 request ID 的持久 mutation receipt，並將部分 Task／Dispatch 接受結果放在同一原生交易。Edict 操作必須保存對應原生 request ID、方法及參數摘要，不能只有本機 operation ID。首次請求 ID 的事先提供及恢復身分須先通過 G-01；公開 --retry-request 的首次使用契約未完成核對前，不私下當作通用首次請求參數。

回應遺失時先用原生 request-show 及既有收據核對；completed、pending、absent 分別處理。pending 可能已含 accepted Dispatch，須納入收件及控制；absent 不證明無副作用，可能涉及未到達、保存或收據保留期。只有原生契約確認可安全重播時，才沿用相同身分、request ID 與完全相同參數；不自動換 ID 重送。原生接受而尚未 ready 的 starting 階段，不能假設 worker-stop 已可執行，須按原生實際可控制階段收斂。

程序在本機送出提交與收據保存之間中斷時，保留名額及範圍，恢復同一操作的核對；新工作世代也不能忽略舊世代仍可能寫入的操作。原生收據有保留範圍與期限，不是永久去重保證。無法恢復原呼叫身分或查清收據時，保留結果未知並回報具體阻礙，不另開相同工作。這些是操作與授權記錄，不取代原生執行狀態。

### 6.2 併發與公平性

本機相同 EDICT_HOME 的階層式 Run 共用准入管理，各 Run 仍有自身上限。首版以本機、單一共享資料目錄為保證範圍；其他主機、其他資料目錄及直接繞過 Edict 的派工不納入 Edict 全域上限保證。

能由原生紀錄辨識的其他 Run 工作，同樣占用本機資源，不能因不屬於本團隊就忽略。這只影響資源准入，不接續或操作其業務。無法確認其身分或範圍時，回傳不確定原因並保守限制衝突工作，不以零占用計算。

執行額度與已開代理程序數分開。目標是讓已確認結束當輪、等待下屬的頭領不占用模型工作額度；但其程序仍占用存續名額。必須由可靠原生事件確認是否等待，不可只看頭領的文字宣告或無輸出就釋放額度。若 Orca 不提供必要狀態或不能限制喚醒執行，需補原生能力，不能宣稱工具已能管制全部模型執行。

首版政策預設每 Run 最多 3 個同時工作的委派，主機總量取既有使用者上限與可用原生上限中的較小值；沒有既有值時以 3 作保守起始值。此數字不是效能結論，須依第 11 節比較結果調整。存續代理上限由實測可承受值決定，未完成主機驗收前不允許無限建立。

有事件待處理的頭領、阻塞中的必要審查優先取得下一個名額；同優先級按工作項目輪流取件，避免一個省部長期占用全部資源。頭領與下屬都計入適用上限，禁止每個團隊各自乘開。

等待中的頭領與子工作不得互為啟動前置。子工作不能依賴「等子工作全部完成才結束」的頭領 Task；關聯用 parent 或成員監督關係表達，真正前置另列。權限檢查也不把尚未產出的方案當成規劃階段的必要前置。

### 6.3 檔案、工具與整合

沿用實體路徑、連結及大小寫別名的衝突檢查。同工作樹只有互不衝突的讀寫可並行；未知範圍保守等待。多位郎中改同一檔案時，依序修改或由 Orca 建立隔離子工作樹，不以不同成員 ID 視為隔離。

工作樹預設 current；真正需要隔離才建立 new-child。new-top-level 仍需使用者明確要求。新工作樹的基準必須包含已核可的前置成果；未 commit 內容需提供可核對快照，不能假定另一工作樹可見。

瀏覽器、測試服務、硬體及專案指定互斥工具列為資源，與檔案範圍一起取得使用權。驗收讀取凍結的成果版本，不能讀正在改動的檔案當作已驗證。

尚書指定實際整合負責部門與郎中，該工作有自己的讀寫範圍及驗收；尚書核對整合結果，不要求所有頭領再各改一次同一批檔案。Git 操作仍按專案規則與既有授權。

### 6.4 可觀察性與流轉紀錄

status 對使用者顯示工作項目、目前省部及成員、階段、等待原因、方案與成果版本，以及最近一項實際進展。開始、交接、退回、核可、驗收、結案與控制操作均保存來源、時間及對應證據，可按工作項目追查。進度呈現可檢查的行為與結果，不要求代理輸出私有推理過程。

採 Orca 現有介面呈現，不以重建原版網頁看板為必要條件；但不能因沒有看板就省略紀錄、目前狀態或人工干預。前端顯示的 Backlog 等名稱不代替領域轉換檢查：缺少門下放行不得進入實作，缺少結案確認不得進入 Done，暫停中的工作不得啟動後續委派。

## 7. 訊息、事件與完成回報

### 7.1 訊息契約

正式訊息包含來源成員、目標頭領、Run、工作項目、訊息用途、方案或成果版本、內容來源及需要的動作。用途限派工、提問、成果提交、審查決定、變更通知等明確型別；一般文字內容不能自行改變派工身分或完成狀態。

```json
{
  "schemaVersion": 1,
  "id": "event-example",
  "runId": "run-example",
  "workItemId": "W-001",
  "kind": "result-submitted",
  "fromMemberId": "member-worker",
  "toMemberId": "member-head",
  "assignmentId": "assignment-001",
  "revision": 2,
  "artifactRef": "artifact-result",
  "nativeMessageId": "message-example"
}
```

此格式是 Edict 領域訊息，不代表 Orca 已接受這些欄位；適配器必須使用實際支援的 message body、Task spec 與收據建立映射。正式來源由執行身分驗證，不直接相信 body 的 fromMemberId。

### 7.2 事件處理

頭領收到事件時，處理同一批可合併訊息、保存證據、核對可啟動工作，再結束當輪，由 Orca 喚醒。下屬的問題先交直接頭領；跨部問題由部尚書交尚書，尚書才按權限轉交。不存在為每個檔案重啟全部三省的流程。

消費去重以原生 message ID 及領域事件 ID 記錄。先把收到的原始事件持久保存，後續動作各有本機操作 ID 及對應原生 request ID；中斷後可續處理。訊息已處理但派工回應未知時，恢復同一操作，不建立新工作。不能聲稱一般網路呼叫能保證恰好執行一次；以收據及原生去重契約避免重複副作用。原生成功是執行事實，取消該工作世代後仍如實保存，但不得因此清除取消或接受為 Done。

中途成果可在代理尚未結束時回報，必須註明暫定與不可據此宣告完成。頭領負責同批整合，只把正式成果與需要決策的問題送出團隊。原對話提供按工作項目的進度，不要求使用者閱讀所有下屬訊息。

### 7.3 頭領任務與成員存續

「本輪等待」與「本次頭領任務完成」分開。頭領發出下屬後可以結束當輪，但尚有本次交付必要子工作時，不能以 worker_done 宣告本次交付完成。原生頭領 Task 與回報路徑的實際支援列為第 11 節驗收。

一批交付確實完成後，頭領可結束該原生 Task；後續差異由 send／continue 續辦，映射回同一邏輯成員。舊 Dispatch 的晚到成果先保存，再由目前有效頭領核對版本與歸屬，不回寫錯誤項目。

## 8. 失敗、停用與恢復

### 8.1 問題歸屬

| 問題 | 接手者 | 處理方式 |
| --- | --- | --- |
| 局部實作或測試失敗 | 部尚書及原作者 | 在原 scope 續辦，審查者核對修正差異 |
| 部門間介面、資源或交付衝突 | 尚書僕射 | 協調相依與分工；需改方案則交中書 |
| 方案缺漏或共同前提不成立 | 中書令、侍中 | 修改受影響方案並重審，不撤銷無關成果 |
| Orca 啟動、回報、儲存或身分未確認 | 對應頭領與執行適配器 | 保留收據與操作意圖，依原生 recovery 指引核對 |
| 需求取捨或新增外部授權 | 太子／原對話 | 詢問使用者必要決策，獨立工作仍可前進 |

### 8.2 不確定結果與重試

無輸出、喚醒延後、啟動逾時或讀不到狀態，都不能單獨證明工作停止。不得因等待而重建 Task、Run、頭領或下屬，也不得用新的代理繞過原生熔斷計數。

只有原生證據確認可以重試、原工作不再執行且授權仍有效時，才按 recovery 指引續辦或重試同一 Task。三次失敗後停止自動修正並指出待驗證假設；原生啟動熔斷與方案審查輪次分別保存，不混為同一計數。

使用者取消時，先持久記錄工作項目、workGeneration、取消意圖、來源、原因及提交序號，再處理既有委派。取消對該代不可撤銷；不論晚到事件、原生 Task 再次 ready、程序重啟或 off 重新啟用，均不得新增業務委派、業務續辦、重試、驗收推進或 Done。收據、成果及停止證據仍可保存，必要的唯讀核對及受控停止屬收尾，不是恢復業務。

取消範圍包含該代所有已建立或在途子委派、後代與未送出的意圖。尚未送出提交的預留撤銷；已提交、結果未知或後來才取得 accepted 收據的操作持續列入取消清冊。對可證明身分且允許停止的 Dispatch 按原生指引處理；starting、stop_unknown、Keep open 拒絕或 queued chat 等情境不得假定已停止。abandon 只能終結派工權，不證明程序已退出或排隊輸入已被移除。

取消完成由事實計算：該代沒有未確認送出或仍可能執行的委派、沒有未釐清的副作用，也沒有仍可能寫入的檔案或工具占用。回覆分為「取消已受理，仍有在途／未確認工作」與「取消已完成」，不將兩者混用。已確認留下的檔案修改及外部效果必須列出；取消不自動回復它們。各原生執行可能是 success、failed 或 stopped，不為了取消結果改寫原生歷史。

同一頭領管理多個項目時，取消只針對指定項目世代及其委派，不因共用 memberId 或頭領程序而停止其他項目。平台不能分離停止共用程序內某項工作時，保留未完成的停止要求並說明限制，不終止整個頭領冒充單項取消。取消完成的項目在工作視圖呈現 Blocked 及獨立控制結果「取消已完成」，不能用 Done 代表取消成功。

resume 只能解除 pause，不能清除取消。使用者明確要求重做時保留工作項目 ID，建立新 workGeneration、新授權及新操作 ID，重新核對適用方案與核可；舊代取消及原生熔斷歷史保留，不能藉換代繞過重試限制。舊成果可被新代明確引用，但舊核可與結案決定不自動沿用。舊代未確認的資源占用仍須收斂。

### 8.3 off 與重新啟用

off 提交後關閉新准入，禁止新的業務續辦及自動向下一階段推進，不取消現有程序；已送出提交的操作依第 6.1 節列為在途。既有代理可完成原委派並回報；收據與成果允許保存，但不因回報而重新啟用或派出審查。主對話列出仍執行、待驗收及結果未知項目。

同一新版環境內重新啟用，沿用原 session、Run、頭領與未完成工作，先核對原生狀態再處理成果；不重建工作，不改已派代理模型或工作樹。跨版本接續不在本方案範圍。

頭領失去上下文時，使用穩定記錄恢復；確認無法恢復且原頭領不再有執行權後，才建立替任。替任與舊頭領不能同時持有有效派工權。不得自動刪除使用者保留的代理或工作樹。

### 8.4 人工暫停與恢復

使用者可指定整個 Run 或一個工作項目暫停。原對話或獲明確控制授權的協調者記錄對象、原因、原生操作身分及控制 revision，作用於其下所有相關委派。暫停是可恢復的流程控制，不等於取消、放棄任務或關閉程序。

暫停提交後關閉尚未取得送出提交的新派工、業務續辦、後續審查及自動結案。已持久送出提交的操作即為在途，包含尚未確認抵達 Orca 的請求；須核對收據並列出，不能宣稱它未曾啟動或保證它稍後不會啟動。已執行代理可以完成既有有界委派並提交成果，頭領只收件及保存，不自動派下一項。工具顯示「已停止接受新派工；仍有在途工作」或「已停止接受新派工；無在途工作」，不聲稱所有實體代理已凍結。

若使用者要求立即停止在途程序，另依第 8.2 節的受控取消執行；平台無可靠程序暫停能力時明確回報，不將流程暫停當作程序凍結。既有讀寫占用直到相應操作確實完成或停止才釋放，不能因已暫停就讓另一位代理修改同一範圍。

領域控制記錄保存 `paused`、控制範圍、來源、原因與 revision；這是獨立控制維度，非第二份原生任務狀態。使用者可見狀態在暫停生效後呈現 Blocked 並註明人工暫停，原階段、在途程序與原生狀態仍可查詢。工作項目暫停不阻擋其他無相依項目；依賴其尚未完成成果的工作須等待。

恢復必須是明確控制要求，且只作用於未取消的同一工作世代。先核對 active 開關、原生在途工作、目前方案與成果版本、有效核可、檔案與工具占用，再解除指定範圍的暫停；不重建 Run、Task 或頭領，不丟棄暫停期間的成果。已失效的方案或成果驗收不因恢復而重新有效。Run 與項目的暫停各自保存，恢復項目不會解除 Run 的暫停。

off 與 pause 分別生效：off 後的 resume 不會重新啟用 Edict；init 也不會默默解除使用者設定的暫停。解除暫停後，原對話或原生事件續辦必要頭領，再按准入檢查啟動原待辦。無可靠事件路由時列出平台限制，不用輪詢或重複派工代替恢復。

## 9. 設定、CLI 與資料保存

### 9.1 模型設定

保留既有角色 ID 與 agent／model／effort。各角色設定代表本省部預設；頭領與執行代理可有明確覆寫，未覆寫即繼承原設定。不得自行更換供應商、模型或推理強度，亦不依工作繁忙程度自動降級。

設定優先順序為本職位明確覆寫、角色既有設定、工具本身預設。模型變更時清除不相容的 effort，換代理時不保留前供應商模型。啟動時保存實際設定快照，之後 config 修改不改執行中的代理；續辦不藉新設定暗中切換模型。

首次 init 仍先詢問共用代理與模型；分職位設定不是啟用的必要問題。有分別設定的需求才詢問缺少值。互動選單的介面實作另案處理。

設定格式使用 `version: 2`，完整保存所有既有 `roles`，新增 `positionOverrides`；其 key 是既有角色 ID，值只允許 `head`、`executor` 的完整 agent／model／effort 組。缺省整組表示繼承，null model 表示明確沿用該代理工具預設。不同代理的設定不做逐欄混合，避免把頭領的模型誤套到另一供應商的執行代理。以下只展示與一個覆寫相關的設定片段，實際存檔仍須包含全部既有角色。

```json
{
  "version": 2,
  "roles": {
    "bingbu": {"agent": "codex", "model": null, "effort": null}
  },
  "positionOverrides": {
    "bingbu": {
      "executor": {"agent": "claude", "model": null, "effort": null}
    }
  }
}
```

此片段說明使用者明確覆寫的格式，不代表自動替使用者選擇兩種代理。`config set <role>` 保留原意；新增 `--position head|executor` 才修改職位覆寫，移除整組覆寫後恢復繼承。

### 9.2 CLI 目標契約

以下均為待新增或擴充介面，非現行 beta.2 已可使用命令。使用者仍只需 init、status、config、off、update、help；內部操作由代理依指引呼叫。

| 操作 | 介面方向 | 必要行為 |
| --- | --- | --- |
| 建立或取得頭領 | team ensure，指定既有 role 與 Run | 重複呼叫取得同一有效頭領；副作用未知時先核對 |
| 建立與啟動工作 | 擴充 dispatch、dispatch-ready；task-create 保留 owner 權限 | 頭領先記錄委派意圖，就緒後以 helper --spec 派工；綁定 workItem、workGeneration、member、supervisor、phase 及核可；owner DAG 使用另外的代建及路由契約 |
| 頭領交涉與續辦 | team send、既有 continue | 檢查真實來源與路由；保留原成員、Run 及新舊 Dispatch 映射 |
| 記錄審查與驗收 | review record，引用成果版本及證據 | 只允許相應審查者或頭領；內部驗收與正式核可分種類 |
| 查詢與設定 | 擴充 status、context、config、doctor | 顯示職位與團隊樹；context 按呼叫者範圍輸出；doctor 區分介面存在與實測能力 |

成員 ID 是查詢目標，不是授權來源。所有寫入操作先驗證原生呼叫身分。範例的 `member` 等參數不能讓一個郎中冒充尚書。

人工控制介面以待新增的 `control pause|resume|cancel` 表達，接受明確 Run 及可選 workItem，不要求使用者輸入內部成員或 Dispatch ID。pause、resume 依第 8.4 節執行；cancel 依原生受控停止及原職權確認。review record 明確區分方案放行、成果驗收與門下結案確認，不能以通用成功結果混用。

使用者可直接在原對話要求暫停、恢復或取消，代理依明確對象呼叫內部介面；不新增每次都必須手動輸入 CLI 的要求。對象有歧義時只詢問需要的工作項目，不猜測取消範圍。

### 9.3 新版記錄與原子寫入

新版 session 與 config 使用 version 2，Run 使用 schemaVersion 2，訊息 envelope 使用 schemaVersion 1；各種欄位分別驗證。只實作新版格式，不增加舊格式 reader、轉換器或並存版本路由。不支援的資料明確拒絕，不猜測轉換、不清除或覆寫原檔。

多個頭領在短鎖內重新讀取、驗證 revision 及局部修改，再以同檔案系統原子替換提交。完整附檔先保存，主檔索引後提交；未引用資料不視為已啟用工作。副作用已發生時，不重試整個派工命令來處理 revision 衝突。

收據保存與派工開關分開，確保同版環境內 off、pause 或 cancel 後仍可記錄在途回應。原生操作與收據核對、事件去重、未確認操作占用及中斷恢復仍為必要可靠性要求，不涉及舊版接續。

Orca 是原生執行狀態來源；Edict 只保存必要身分、授權、證據與操作記錄，不複製 inbox 或背景消費郵件。紀錄不含 token、密碼或憑證；此方案不要求重做安裝或更新器。

| C-02 | 兵部內部審查代替刑部 | 核可方案要求的刑部程式、功能或合規驗收仍須完成；作者不能免除，也不能審核自己參與製作的成果 |
| C-03 | 暫停、恢復與 off 交錯 | 暫停不新增後續委派，保留在途成果及占用；恢復不重派、不解除其他層暫停、不自行啟用 off 的對話 |
| C-04 | 太子底層啟動與省部交涉 | 門下審查及尚書調度可追溯到合法發起者；控制操作不能跳過中書送審或門下核可 |
| C-05 | 單項、批次與續辦入口 | 對未核可實作皆在原生副作用前拒絕；讀取與保存回報仍可執行；無入口能只靠協調者填 approved 放行 |

### 11.5 成效判斷

以相同需求、專案基準、代理與模型設定、主機資源及驗收要求比較既有模式與階層模式。至少包含單項小任務、多項獨立任務、共享介面任務三類；每類至少三次，報告中位數、範圍、失敗及未完成樣本，不只挑選最快一次。

記錄需求送出至首次實作開始、總完成時間、規劃與審查耗時、轉交及重工次數、代理峰值與可取得的 token／費用。供應商未提供的計量寫明缺測，不估成已知值。測試及審查要求一致，不能靠省略驗收取得速度差。

多項獨立任務必須證明實際分工及平行，且總完成時間有改善；單項小任務不得為維持組織形式固定增加無用代理。改善幅度由量測報告支持，本設計不承諾固定百分比。正確性、權限或整合失敗時，即使更快也不通過驗收。

## 12. 依據與設計解讀

### 12.1 本機程式與指南

- `src/roles.mjs`：角色 ID、現行派工限制與 workerSpec；對應職位、委派及通訊責任。
- `src/cli.mjs`、`src/config.mjs`、`src/session.mjs`：命令入口、設定、對話啟用、原子寫入及收據索引；對應統一檢查、新版資料與在途回報。
- `src/schedule.mjs`、`test/schedule.test.mjs`：逐 scope 核可、原生就緒查詢、讀寫衝突與續辦案例；既有能力須保留，不能將它們當作本設計新增成效。
- `orca skills get orchestration` 及其 coordinator-loop、recovery-and-cleanup 參考，與 `orca orchestration worker-start --help`：使用實際安裝的指南，遵循事件喚醒、原生相依及不確定結果的恢復限制。
